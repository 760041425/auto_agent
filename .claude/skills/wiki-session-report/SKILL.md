<!-- wiki-common-rule:v1 -->
## 0. 通用交互与汇报规约（全技能通用 · 优先级高于下文具体步骤的表述习惯）

**语言**：面向用户的所有叙述、标题、汇报一律用**简体中文**（代码 / 命令 / 路径 / 标识符 / 引用的英文报错原文除外）。即使 subagent、工具或 CI 返回英文或日文，回写给用户时必须翻成简体中文，全程不得切换语种。

**收尾汇报**：本技能每跑完一个阶段或全部完成时，**必须**：
1. 用 Markdown **表格**汇报结果（典型列：步骤 / 事项、状态、产物或证据链接、备注）；
2. 表格后另起「**下一步建议**」小节，给出 **1–3 条可直接执行**的动作——可复制的 shell / `gh` 命令，或 `/wiki-*` 串联指令；禁止只写「可以继续优化」这类空话。

<!-- hardening-rules:v1 (skill-mining 2026-06-10) -->
## 硬化规约（数据挖掘驱动 · v1）
- **shell**：多行 shell 片段与 `source issue-claim.sh` 一律 `bash -c '...'` 显式执行；禁止依赖交互 shell（zsh 只读变量 status / `export -f` 不兼容 / 分词语义差异）。
- **gh**：写操作（comment / label / merge / api PATCH / close）必须 `_gh_retry 3 2 -- gh ...` 包裹（来源 wiki-issue-claim-lib，EOF/超时/5xx/限流自动退避重试）。
- **等待**：等 CI / 任务 / 部署一律 Bash `run_in_background: true` + Monitor/TaskOutput 收口；禁止 `sleep N && cat` 前台轮询（会被 harness 拦截）。
- **AskUserQuestion**：单次 ≤4 题、每题 2–4 个选项；>4 题拆多次背靠背连发；禁止发空 `questions`。
- **devlock**：取锁三段式 `lock_try_acquire` → 失败 `lock_status` 查持锁者 → 超 10 分钟无心跳 `lock_reap` 后重试；禁止无界裸 `lock_acquire`。

<!-- parallel-default-rule:v1 -->
## 0. 并行化默认规则（全技能通用）

**当本技能识别出任务可拆为 ≥5 个相互独立的子单元**（典型：spec / 模块 / 文件夹 / Issue / 用例文件 / 镜像 / 子页面 / 子图等），**优先**走以下骨架，**不要**顺序硬扛：

1. 用一个前台 subagent 完成调研 + 拆分，输出 5–30 个独立工作单元（每个单元可单独完成、无相互依赖）。
2. 对每个单元用 `Agent` 工具发起后台 subagent，参数固定：
   - `isolation: "worktree"`（隔离的 git worktree，避免互踩）
   - `run_in_background: true`（并行执行，不阻塞协调者）
   - `subagent_type` 按任务类型选（默认 `general-purpose`）
3. 在一条消息里一次性发起全部 subagent（多 Agent 工具调用并列），最大化并行度。
4. 协调者只负责：渲染进度表 → 收 PR 链接 → 汇总状态。
5. 单元数 <5、或单元之间存在强依赖时，直接顺序处理，**不要**为并行而并行。

**红线**：
- 涉及非 git 仓库的目录（如 `~/.claude/skills/`、本机配置文件）→ 不能用 worktree，退回顺序模式。
- 单个单元预计 <2 分钟可完成 → 起 subagent 的开销得不偿失，直接做。
- 单元之间共享状态（同一文件、同一数据库行、同一端口）→ 强制顺序，不许并行。

参考骨架：`/batch` slash command。

# /report — 对话进展汇报（白话三段式）

## 1. 触发场景

- 用户说："/report"、"汇报一下"、"写个进展"、"总结这轮"、"给我一份进度"、"输出进展给老板/同事看"。
- 用户在一段较长的工作会话末尾，想把刚刚做的事**沉淀成一份可转发的材料**。
- **反例**：用户只是想要技术细节、想看完整 diff、想读运行日志——直接答即可，不要触发本技能。

---

## 2. 硬性产出规则（缺一不算合格）

| 维度 | 要求 |
|---|---|
| 总字数 | **≤ 300 字（中文按字计，英文按词计；标题/表格不计入硬上限，但也要克制）** |
| 段落结构 | **严格三段**：① 背景 ② 进展 ③ 待办（顺序、标题不变） |
| 段落比例 | 大致 **背景 25% / 进展 50% / 待办 25%**，不要头重脚轻 |
| 表格优先 | "进展"和"待办"段**必须**至少有一张表；纯散文不允许 |
| 语言风格 | **文科生友好**：少术语、不堆代码、不贴路径、不抄日志；必须出现的技术名词要顺手用一句话/括号注解 |
| 客观度 | 只写**已经发生**或**已经决定**的事；不评价、不吹、不写"非常顺利""效果显著"这种主观词 |
| 链接 | 涉及具体文件 / PR / Issue 时，用 markdown 链接挂上，但**链接文本要人话**（不是裸 SHA / 裸路径） |

---

## 3. 模板（直接套用，按需替换占位符）

```markdown
## 📋 本轮进展汇报

### 一、背景
> 用 2–3 句白话讲清「这轮在做什么、为什么要做」。
> 不写技术细节，让没参与的人也能 30 秒内 get 到大方向。

### 二、进展

| 事项 | 状态 | 一句话说明 |
|---|---|---|
| {{做完的事 1}} | ✅ 已完成 | {{做了什么 / 解决了什么}} |
| {{做完的事 2}} | ✅ 已完成 | {{...}} |
| {{进行中的事}} | 🟡 进行中 | {{当前卡在哪 / 下一步要做啥}} |
| {{暂停的事}} | ⏸️ 暂停 | {{为什么暂停}} |

（可选）一句话补充：本轮关键决策 / 风险 / 意外发现，**最多两句**。

### 三、待办

| 优先级 | 任务 | 负责人 / 何时做 |
|---|---|---|
| P0（必须） | {{下一步必做的事}} | {{谁 / 何时}} |
| P1（重要） | {{...}} | {{...}} |
| P2（可选） | {{...}} | {{...}} |
```

---

## 4. 执行步骤（Claude 收到 /report 时按此办）

1. **回看本轮对话**：从最近一次用户主题切换开始，提取「目标 → 做过的动作 → 当前状态 → 未完成项」。
2. **去技术化改写**：
   - 把 "修复了 `web/bff/api/handlers/auth.py:42` 的 NPE" → 改成 "修复了登录接口的一个崩溃问题"。
   - 把 "重构 K8s deployment 的 rollingUpdate 策略" → 改成 "调整了线上服务的更新方式，避免发版时短暂中断"。
   - 必须出现的术语，加一句白话注解，例："CI（自动化测试流水线）"。
3. **填模板**：严格按三段结构，进展和待办都用表。
4. **字数自检**：写完通读一遍，删冗余形容词、删"我们""目前""接下来"等口水词，压到 300 字以内。
5. **客观度自检**：删掉所有自我评价（"顺利"、"高效"、"质量很高"、"非常成功"），只留事实。
6. **链接自检**：如果引用了 PR / Issue / 文档，文本必须是人话，不能是 `#1234` / `abc123f`。

## 5. 自检清单（输出前过一遍，任一不过 → 重写）

- [ ] 三段标题齐全且顺序正确（背景 / 进展 / 待办）
- [ ] 总字数 ≤ 300
- [ ] 进展段有表格，待办段有表格
- [ ] 没有出现裸代码片段 / 裸文件路径 / 裸日志
- [ ] 没有出现主观评价词（顺利 / 高效 / 完美 / 漂亮 …）
- [ ] 一个非技术同事读完，能说出"这轮在干嘛、做完没、下一步啥"
- [ ] 必要的链接都挂了，且链接文本是人话

## 6. 反例（不要这么写）

❌ **太技术**：
> "本轮在 `algo/contexts/region-segmentation-context/` 下重构了 `SegmentationService.run()`，把同步阻塞改成 asyncio.gather 并发，p99 从 1.2s 降到 380ms。"

✅ **改写后**：
> "本轮优化了一个图像分割接口的速度，从约 1 秒缩到 0.4 秒，用户那边会感觉明显变快。"

❌ **太主观**：
> "进展非常顺利，所有目标都圆满完成，质量很高。"

✅ **改写后**：
> "本轮 3 项任务全部完成，剩余 1 项待下周继续。"

❌ **散文堆叠没有表**：
> "我们先做了 A，然后做了 B，接着又做了 C，最后还做了 D……"

✅ **改写后**：用表格列出 A/B/C/D 的状态。
