# Wiki Issue Design

把需求想清楚并沉淀为仓库权威规格。不要实现业务代码。

## 权限边界

- 先读取仓库根 `AGENTS.md`、`CLAUDE.md`、`docs/`、`contexts/` 和现有 `specs/`；仓库规则优先。
- 创建或更新本地设计文档属于本技能范围。
- 只有用户明确要求创建/更新 GitHub Issue 时才执行外部写操作。
- 不提交、推送、合并或切换受保护分支，除非用户明确授权。
- 需要当前市场、竞品、规范或库信息时浏览互联网，优先官方和一手来源并给出链接。
- 只在会改变范围、数据模型、用户体验或交付策略的决策上询问用户；其余用明确假设继续。

## 1. 建立设计上下文

1. 确认用户目标、受影响角色、当前痛点、期望结果和时限。
2. 检查现有功能、相关规格、测试和未提交改动，避免重复需求。
3. 将信息分为：已确认事实、工作假设、开放问题、非目标。
4. 若用户只要求讨论，不创建文件；若要求整理/设计，按仓库规则创建规格资产。

## 2. 用 DDD 定边界

确定：

- 所属子域和限界上下文；
- 统一语言中新增或变化的术语；
- 上下游契约、数据所有权和防腐层；
- 领域规则与接口/数据库/第三方适配的分界。

领域术语或边界发生变化时，同步更新项目指定的长期文档。

## 3. 用 SDD 形成变更包

优先使用仓库约定的 `specs/<feature-id>/`。若仓库没有约定，采用：

- `spec.md`：目标、范围、用户故事、带稳定 ID 的验收标准；
- `clarify.md`：事实、假设、已决与开放问题；
- `plan.md`：上下文、数据流、模块、迁移和回滚；
- `tasks.md`：按依赖排序、带完成证据的任务；
- `checklist.md`：Definition of Ready/Done；
- `testlist.md`：主路径、失败、边界和非功能场景；
- `risks.md`：风险、触发信号、缓解和回滚；
- `decisions.md`：已批准决策及后果。

完整模板见 [references/spec-package.md](references/spec-package.md)。

要求：

- 每条验收标准可观察、可判定，并使用 `AC-<spec>-<NN>`。
- 每个 AC 至少映射一个 `TL-<spec>-<NN>`。
- 不把技术方案写成用户价值，也不把论文/竞品数字当成本项目承诺。
- 不能确认的内容进入 `clarify.md`，不要自行拍板。

## 4. 方案与原型

- 给出 1 个推荐方案；只有存在真实取舍时再给 2–3 个备选。
- Web/UI 变更先读取项目 UI 规范和现有组件。代码原型优先复用当前技术栈；视觉探索才使用图像生成。
- 方案说明包含数据流、状态机、错误路径、迁移、兼容、观测和回滚。
- 对高成本或不可逆选择，暂停并请求用户决策。

## 5. 评审与校验

检查：

- 需求、上下文、计划、任务和测试能否互相追踪；
- 是否遗漏失败、权限、并发、幂等、恢复、删除和兼容场景；
- 是否与现有代码、API、数据库和部署约束冲突；
- 文档中的实现状态是否有证据。

运行仓库已有的规格校验和漂移检查。失败时修正文档；环境缺失时记录阻塞，不伪造通过。

## 6. 可选创建 GitHub Issue

仅当用户明确要求时：

1. 先搜索现有 Issue，避免重复。
2. 优先使用可用 GitHub 连接器；没有时检查已认证的 `gh` CLI。
3. Issue 正文包含背景、目标、范围、AC、非目标、规格链接、风险和完成定义。
4. 创建后读取返回结果并报告真实 URL。
5. 不自动创建分支、提交、推送或启动开发。

## 收尾

使用简体中文表格列出产物、状态、开放决策和验证结果。最后提供 1–3 个直接动作；如果适合进入实现，建议显式调用 `$wiki-issue-dev`。
