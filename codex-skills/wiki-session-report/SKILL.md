# Wiki Session Report

把本轮任务压缩成非技术读者也能理解的客观汇报。

## 工作流

1. 回看当前任务的目标、实际变更、验证结果、阻塞项和未完成项。
2. 只写有证据支持的事实。不要把“已创建”“已运行”“已部署”“已安装”混为一谈。
3. 将实现细节改写为业务影响；必要术语后补一句白话解释。
4. 引用真实文件时使用 Codex 可点击的绝对路径链接；引用外部对象时使用实际 URL。
5. 控制正文在 300 字以内，标题和紧凑表格不计入正文预算。

## 固定结构

逐字使用以下四个标题，不得省略“一、二、三”、图标或“下一步建议”。不要把标题改成无序列表或纯散文。

```markdown
## 📋 本轮进展汇报

### 一、背景

用 2–3 句说明任务和原因。

### 二、进展

| 事项 | 状态 | 结果或证据 |
| --- | --- | --- |
| ... | ✅ 已完成 / 🟡 进行中 / ⏸️ 阻塞 | ... |

### 三、待办

| 优先级 | 任务 | 条件或负责人 |
| --- | --- | --- |
| P0/P1/P2 | ... | ... |

#### 下一步建议

给出 1–3 个可直接执行的动作。
```

## 自检

- 输出前逐项检查标题必须精确包含：`## 📋 本轮进展汇报`、`### 一、背景`、`### 二、进展`、`### 三、待办`、`#### 下一步建议`。
- 进展与待办各至少有一张表。
- 不写主观评价，不复述长日志，不暴露密钥或内部凭据。
- 验证失败、仅局部通过和环境未覆盖必须显式说明。
- 不声称进行了未获授权的 Git、GitHub、部署或消息发送操作。
