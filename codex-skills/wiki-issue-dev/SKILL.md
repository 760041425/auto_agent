# Wiki Issue Dev

将已批准需求落实为经过验证的代码。需求仍模糊时先使用 `$wiki-issue-design`。

## 不可跳过的边界

- 读取根 `AGENTS.md`、`CLAUDE.md`、相关 `docs/`、`contexts/`、规格包和测试。
- 保护工作区中无关的未提交改动；不要用 reset、checkout 覆盖或递归删除。
- 用户要求“实现”不自动授权创建 Issue、推送、合并、部署或关闭 Issue。
- 如果用户明确要求完整 Issue 闭环，可执行该范围内的 GitHub 写操作，但仍须遵守受保护分支和发布约束。
- 不硬编码仓库、分支、namespace、URL、凭据或 deployment 名；从项目文档和当前环境读取。
- 不打印包含令牌的 remote URL、环境变量、kubeconfig 或认证内容。

## 1. 预检

1. 确认仓库根、当前分支、工作区状态和相关文件；记录哪些改动不是本任务产生的。
2. 定位现有 Issue/规格。若用户给 Issue，读取正文、评论、标签和关联 PR；无 GitHub 工具时用已认证 `gh`，否则报告缺口。
3. 确认规格状态、AC、开放问题、上下文归属和发布限制。
4. 运行现有基线测试，或至少运行与变更最近的测试。把环境失败与行为失败分开。
5. 若方案选择会显著改变范围、数据模型、API 或迁移，先请求用户决策。

## 2. 同步规格和计划

- 缺少规格包时创建项目要求的文件；已有时只做当前变更所需增量。
- 为 AC、任务和测试场景使用稳定 ID。
- `plan.md` 写清模块、依赖方向、数据/接口迁移、观测和回滚。
- 把任务拆成可独立验证的小步，一次只推进一个行为。
- 若用户尚未批准关键技术方案，先展示简明方案与风险，不开始不可逆实现。

## 3. TDD 实现

对 `testlist.md` 中每个选中场景执行：

1. **Red**：增加一个最小失败测试，确认失败原因正是缺失行为。
2. **Green**：只写足以通过该测试的实现。
3. **Refactor**：相关测试全绿后整理结构，不改变外部行为。
4. 更新 `tasks.md`、`testlist.md` 和必要的决策/风险记录。

实现约束：

- 接口层只做协议转换，应用层做编排，领域对象/策略表达业务规则；
- 数据库、文件、外部 API、模型和消息系统通过适配边界接入；
- 修复同模式位置前先搜索影响面，避免只改首个命中；
- 不顺手修改无关文件或扩大需求范围。

## 4. 分层验证

按风险执行：

- L1：单元与领域契约；
- L2：API、数据库、文件系统和外部适配集成；
- L3：真实用户路径或系统测试；
- 非功能：性能、安全、恢复和兼容（规格要求时）。

Web 行为优先使用已安装的浏览器控制 skill，保存截图、console 和 network 证据。K8s 只在项目明确指定且当前凭据可用时验证；不要用本机 Docker 冒充指定环境。

测试失败时定位原因并继续修复，除非失败来自缺少权限、用户决策或外部状态。不要把未运行写成通过。

## 5. Review 与追踪

1. 对照 AC、计划和测试检查实现漂移。
2. 审查错误处理、并发、幂等、迁移、权限、日志、兼容和回滚。
3. 运行仓库要求的规格校验、快速测试、静态检查和漂移检查。
4. 生成或更新追踪矩阵：AC → TASK → TL → 测试/证据。
5. P1/P2 发现优先修复；超出范围的独立问题记录为待办，不偷偷扩散。

证据格式见 [references/completion-evidence.md](references/completion-evidence.md)。

## 6. Git、GitHub 与部署

只有获得相应授权才执行：

- 创建或切换分支；
- stage、commit、push；
- 创建/更新/合并 PR；
- 部署、rollout、数据库迁移；
- 评论或关闭 Issue。

执行前用只读检查解析精确目标。受保护分支必须遵循项目规则，不直推绕过。每个写操作后读取真实结果；失败时不声称成功。

关闭 Issue 的最低条件：

- 所有 P0 AC 通过；
- 规格、任务和测试状态真实；
- 所需环境验证完成；
- 变更已存在于用户要求的目标分支/版本；
- 评论包含测试、部署（如适用）、review 和已知限制证据。

任一条件不满足时保持 Issue 打开并说明阻塞。

## 收尾

用简体中文表格汇报规格、实现、测试、环境、Git/GitHub 状态和剩余风险。若用户需要可转发短报，再使用 `$wiki-session-report`。
