# Wiki Bug Fix

用可重复证据修复根因，不只消除表面症状。

## 安全与权限

- 先读项目 `AGENTS.md`、`CLAUDE.md`、相关规格、上下文和测试。
- 保护无关未提交改动；禁止 reset、强推、覆盖用户文件或无界清理。
- 生产系统默认只读诊断。部署、重启、回滚、写数据库和关闭 Issue 需要明确授权。
- 用户要求“修 Bug”授权本地代码与测试修改，不自动授权 GitHub、Git 或部署写操作。
- 不输出令牌、带凭据的 URL、认证头、kubeconfig、客户数据或内部地址。

## 1. 确认 Bug 身份

整理：

- 期望行为及其规格/契约来源；
- 实际行为、错误原文、首次出现版本和影响范围；
- 输入、环境、频率、严重度和可用绕行；
- 已有 Issue、PR、日志、截图和监控证据。

如果实际行为符合当前规格，这可能是需求变更而非 Bug。记录差异并转 `$wiki-issue-design`，不要擅自改语义。

## 2. 精确复现

1. 从最小、确定性路径开始，在允许的最低风险环境复现。
2. 记录命令/操作、输入、版本、时间窗口、预期和实际结果。
3. Web Bug 使用浏览器控制 skill 重放真实用户路径，收集截图、console 和 network。
4. API/任务 Bug 保存请求、响应、状态流转和相关日志。
5. 数据/算法 Bug 使用最小夹具并记录随机种子、模型/数据版本和硬件。
6. 无法复现时列出已排除因素和下一观测点；不要猜根因。

## 3. 根因分析

执行 5 Why，但每一层都要有代码、测试、日志、历史变更或契约证据。区分：

- 直接触发点；
- 真实根因；
- 为什么现有测试/监控没有发现；
- 同模式代码的潜在扩散位置；
- 修复可能改变的兼容与数据语义。

搜索仓库历史、相关规格和现有测试。只有项目提供受控 memory/知识库时才读取；不要依赖其他代理的私有目录。

## 4. 规格增量

在所属规格包中新增或更新 Bug 记录。模板见 [references/bugfix-template.md](references/bugfix-template.md)。

至少包含复现矩阵、5 Why、影响面、修复策略、扩散排查、回归场景、风险和回滚。新增/改变外部行为时同步 AC、testlist 和决策；纯实现错误不改写正确验收口径。

## 5. 回归 TDD

1. **Red**：先增加能稳定复现原 Bug 的测试，确认修复前失败。
2. **Green**：做最小根因修复，使回归测试通过。
3. **Refactor**：相关测试全绿后整理。
4. 对同模式位置建立覆盖矩阵；只修有证据、在范围内的位置。
5. 运行近邻测试和项目要求的快速/全量门禁。

回归测试应证明旧实现会失败，而不是只覆盖修复后的 happy path。

## 6. Before/After 验证

- 使用与复现阶段相同的输入、路径和环境；
- 证明原症状消失，同时关键正常路径不退化；
- 对抗式寻找“仍能复现”的反证；
- 环境验证时核对实际部署版本，避免在旧版本上误判；
- 记录未覆盖环境和剩余风险。

若测试环境或凭据缺失，完成本地修复后明确标记“环境未验”，不得关闭需要该门禁的 Issue。

## 7. Review 与可选收口

Review 检查根因、测试真实性、兼容、并发、错误处理、迁移、扩散和回滚。

只有用户授权且以下条件满足时更新/关闭 Issue：

- 回归测试先红后绿证据成立；
- 原路径 Before/After 通过；
- 规格要求的环境验证完成；
- 修复已进入目标版本；
- 无未解决 P0/P1；
- Issue 评论包含 RCA、测试、扩散矩阵和已知限制。

否则保持打开并报告阻塞。Git 提交、推送、PR、合并、部署同样需要各自授权和项目规则允许。

## 收尾

用表格汇报复现、RCA、规格、回归、扩散、环境和外部操作状态；列出 1–3 个直接下一步。需要短版汇报时调用 `$wiki-session-report`。
