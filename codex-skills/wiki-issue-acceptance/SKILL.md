# Wiki Issue Acceptance

以规格为唯一判定基准，证明功能是否可接受。不要用“代码看起来正确”代替真实验证。

## 权限和判定边界

- 先读根 `AGENTS.md`、`CLAUDE.md`、相关规格、上下文、代码和已有测试。
- 默认执行只读检查、测试和报告；“验收”本身不授权修改业务代码、推送、部署或关闭 Issue。
- 用户明确要求“验收并修复”时，可在范围内修改代码和测试；Git/GitHub/部署仍按各自授权执行。
- 规格缺失或自相矛盾时结论为“不可判定”，先补规格或请求决策。
- 测试环境由项目文档定义。不得用本机 Docker 冒充指定 K8s/远程环境，也不得把本地通过等同于已部署通过。
- 不读取或输出秘密；证据中的令牌、个人数据、内部地址和客户内容必须脱敏。

## 1. 建立验收目标

1. 定位 Issue/规格版本、目标提交或部署版本。
2. 提取全部 P0/P1/P2 AC、非目标、风险和环境门禁。
3. 为每个 AC 标记：可测试、需用户决策、需外部环境或不适用。
4. 检查现有测试能否真实覆盖行为，而不是只断言 mock。

## 2. 设计测试矩阵

按 AC 和风险确定数量，不机械追求固定条数。至少考虑：

- L1：领域规则、值对象、策略、schema/契约；
- L2：API、数据库、文件、队列和第三方适配；
- L3：真实用户操作、页面渲染、console 和 network；
- 横向：成功、失败、边界、权限、并发、幂等、恢复、兼容；
- 非功能：性能、安全、可观测和回滚（规格要求时）。

每条用例使用稳定 ID，并记录 AC、前置条件、步骤、预期、环境和证据位置。模式见 [references/test-patterns.md](references/test-patterns.md)。

## 3. 环境预检

### 本地

- 验证依赖、夹具、测试命令和工作区状态；
- 记录基线失败，区分环境问题与产品问题。

### K8s/远程环境

仅当项目明确指定时：

1. 从项目文档读取 kubeconfig、namespace、URL、deployment 和版本策略；
2. 先做只读连通性、身份和权限检查；
3. 记录实际部署镜像/提交，确认它包含待验版本；
4. 默认只读观察。rollout、scale、restart、patch、数据库写入或清理需要明确授权；
5. 故障诊断参考 [references/k8s-debug.md](references/k8s-debug.md)。

环境不可达时继续完成可做的 L1/L2，并把依赖该环境的 AC 标记为 blocked/not run。

## 4. 执行与留证

- 先执行最小、确定性的用例，再进入昂贵或破坏性验证。
- 保存命令、退出码、关键输出、版本、时间上下文和测试数据标识。
- Web 验收使用浏览器控制 skill；验证用户路径、渲染、console 和非预期 4xx/5xx，并保存截图。
- API 验收保存脱敏请求/响应；数据库检查优先只读查询。
- 每个失败至少复跑一次或用独立方式确认，排除偶发与测试缺陷。
- 不因等待 CI/任务而长时间沉默；使用可用的监控/等待工具并持续更新。

## 5. 对抗式证伪

在准备判定通过前主动寻找反证：

- 使用边界、非法、重复或并发输入；
- 刷新/重启后验证状态是否仍正确；
- 确认前端不是缓存或旧 bundle；
- 确认测试没有 mock 掉被验收边界；
- 确认部署版本不是旧提交；
- 检查成功路径之外的错误信息、补偿和恢复。

存在可信反证时不得判通过。

## 6. 报告

在项目指定位置生成 `acceptance.md`；没有约定时放入对应规格包。至少包含：

```markdown
# <Spec/Issue> 验收记录

## 验收目标与版本
## 环境
## AC 追踪矩阵
## 测试结果
## 失败与证据
## 对抗式复核
## 已知限制
## 结论
```

状态只使用：

- `pass`：要求已实际验证；
- `partial`：只覆盖部分路径/环境；
- `fail`：观察结果不符合规格；
- `blocked`：缺权限、环境或决策；
- `not run`：未执行。

只有全部必需 AC 为 pass 且环境门禁满足时，结论才是“验收通过”。

## 7. 可选修复和收口

若用户明确要求修复：

1. 为失败行为先补回归测试；
2. 按 Red → Green → Refactor 修复；
3. 重跑失败用例、近邻回归和完整门禁；
4. 更新 `acceptance.md`，保留修复前失败证据。

只有用户授权、目标版本已部署、必需 AC 全通过且无未解决 P0/P1 时，才可评论或关闭 Issue。否则保持打开。

## 收尾

用简体中文表格汇报 AC 通过率、环境覆盖、失败/阻塞、代码修改和外部操作。列出 1–3 个可直接执行的下一步。
