# BUG-003-03 — 查询图坐标转换能力未迁入定位任务

日期：2026-08-01  
状态：已修复

## 现象与证据

- 参考工程文档描述了查询图归一化选点、单应矩阵得到 SLAM XY、同位置投影 NPY 返回 XYZ 的用户路径。
- `opencode-demo` 最初只有未接线的远程适配器，定位任务本身不生成 H/最终位姿 XYZ NPY，前端也没有可靠的任务级上下文。
- 用户明确要求不启动、不联调参考工程，将能力完整迁移进当前项目。

## 5 Why

1. 为什么页面没有坐标？查询图最初只是静态 artifact。
2. 为什么加代理仍不满足？代理要求另一个服务和 camera 数据库同时可用。
3. 为什么当前任务不能自己回答？结果只保存位姿和图片，没有保存 query→SLAM H 与像素级世界 XYZ。
4. 为什么生成流程漏掉它？artifact 契约只覆盖 PNG，没有覆盖交互式坐标查询所需的 NPY/矩阵。
5. 根因是什么？坐标转换被错误划为外部应用能力，没有归属空间定位结果聚合。

## 修复

1. V2 runner 保存最终采用的 2D–3D 内点，并拟合 query pixel→SLAM XY 单应矩阵。
2. 使用最终 PnP 位姿投影地图点，按最近深度 z-buffer 和 3×3 splat 生成与查询图对齐的 XYZ NPY。
3. `LocalizationResult.coordinate_transform` 持久化 H、NPY 路径、尺寸和拟合计数。
4. 本地 `/api/localize/coordinate-transform` 按 `task_id/result_index/u/v` 查询，不使用 URL、HTTP、camera_id 或外部数据库。
5. 前端仅对 `coordinate_transform.status=ready` 的新结果开放选点；历史结果提示重新定位。
6. 坐标差属于 H/NPY 内部一致性，独立位姿 Benchmark 仍为 Phase B TODO。
7. 后续纠偏：坐标差不再只供点击查看；定位自动采样最多 256 个有效点，以中位差严格 `<0.3m` 作为 V2 唯一可信门槛，等于或超过均不准，内点/相似度降为辅助诊断。

## TDD

- Green：本地 z-buffer、H 拟合、有效/无效 NPY 点、API 任务归属和前端静态契约测试通过。

- task #223：LoFTR 定位成功，22 内点，位姿 `[30.46, 4.08, 7.81]`。

- API 有效点示例：H→SLAM `[-21.565, 36.079, 0]`，NPY `[-23.087, 20.852, 0.087]`，差值 `15.303 m`。
- 浏览器点击示例：页面同时展示两套 XYZ 与 `35.030 m` 差值，并声明非绝对精度。
- 最终页面复核：独立的 2D 拟合未执行时不再伪造 `0/0`，本地坐标卡显示 H 内点 `20/22`。
- 门禁：严格 0.3 m 规则落地后，最终 fast `61 passed, 4 deselected`；规格校验、JS 语法、diff check 和漂移检查通过（0 error，6 条既有历史产物 warning）。

## 最终可信判据纠偏

- task #225 与此前样本相同，仍得到 22 个 PnP 内点和相同位姿，但自动采样 256 个有效 NPY 像素后，中位坐标差为 `28.448 m`、P95 为 `200.674 m`。
- 最终门槛经用户确认为严格 `<0.3 m`；该样本远超门槛，因此 API 返回 `success=true, reliable=false`，高内点不能覆盖坐标差失败。
- 浏览器主卡显示“坐标差最终判定 / 未通过 / 低可信”，原 2D 拟合与独立 Benchmark 收入折叠的辅助诊断区。
- task #226 使用 API 默认参数重新定位，结果持久化 `threshold_m=0.3`、`median_m=28.448`、`passed=false`、`reliable=false`，证明默认门槛在真实任务链路生效。
- 浏览器复核 task #226：主卡显示“判定门槛: < 0.300 m；结论: 未通过 / 不准”，并正常显示查询图像与最终位姿投影图。
