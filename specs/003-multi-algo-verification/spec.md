# 003 多方案定位与可信验证修复

状态：Phase A 已实施并通过快速门禁；Phase B 标记为 **TODO（暂时遗留）**  
上下文：空间定位、任务与影像；地图准备为上游依赖

## 背景与目标

当前分支新增 DISK+LightGlue、LoFTR、Hybrid、ACE+LAS 和 Multi-Strategy 五条实验路径，同时增加日志分离、投影验证、benchmark 和 HTML 报告。修复前存在算法注册与运行分派不一致、比较任务缺少 `Path` 导入、验证逻辑自比较、结果字段被 API 适配层丢弃、报告不可独立复现等问题；Phase A 已修复这些确定性缺陷。

本变更首先恢复所有公开路径的真实可运行性，然后建立不循环论证、可追踪、可复现的定位评估方式。没有独立真值时，报告只能表达几何拟合或地图一致性，不能宣称绝对定位精度或最终推荐算法。

## 范围

### In Scope

- 建立单一算法注册表，使 UI/API 算法 ID 精确映射到对应 runner；
- 定义稳定的 `LocalizationResult` 与验证结果契约，保留失败诊断；
- 修复 `Path`、`best_pose`、运行目录、日志 handler 等确定性回归；
- 区分重投影误差、投影一致性、LAS 邻近性和独立真值误差；
- 让 benchmark 固定数据集、配置、随机种子和运行环境，并生成唯一运行 ID；
- 补齐 API、领域工具、报告和干净启动测试；
- 修正文档中未经证据支持的完成状态与算法推荐。

### Out of Scope

- 本变更不训练新模型，不承诺提升算法精度；
- 不一次性搬迁 `api/`、`services/` 的全部物理目录；
- 不引入分布式任务队列或重做任务状态机；
- 不把论文或两张样本图的结果作为生产性能承诺；
- 不在没有真值数据的情况下决定最终定位算法。

## 用户故事

- 作为操作人员，我选择某个算法后，系统实际运行的算法必须与 UI 标签一致。
- 作为算法工程师，我能区分“PnP 拟合良好”“与地图点接近”和“相对真值准确”三种不同结论。
- 作为评审者，我能从报告中复现数据集、参数、代码版本和随机种子，并判断推荐是否有充分证据。
- 作为维护者，我能在干净克隆中启动服务，并从日志中定位具体任务与算法失败原因。

## 验收标准

- **AC-003-01**：通过 API 分别选择五个公开算法 ID 时，每个 ID 只调用其注册的 runner；未知 ID 返回 422，算法异常不会串到其他实现。
- **AC-003-02**：每个算法返回统一结果契约，至少包含 `algorithm_id`、`success`、`reliable`、`pose`、`quality`、`validations`、`artifacts`、`timings` 和结构化 `error`；旧任务结果仍可读取。
- **AC-003-03**：几何求解成功与最终可信分开表达；算法无解是可观察领域结果，内部异常保留错误码和诊断信息。没有新判据的旧算法暂以 `min_inliers` 兼容判定，V2 必须使用 AC-003-14 的坐标差标准。
- **AC-003-04**：验证输出明确标注指标类型；同一 NPY 自比较不得产生“绝对 3D 精度”，无独立真值时绝对精度字段为 `null/not_available`。
- **AC-003-05**：提供真值时，报告至少输出平移误差（米）和旋转误差（度）；报告能追溯数据集清单、配置、种子、硬件/设备、代码提交和运行时间。
- **AC-003-06**：报告使用唯一 `run_id`，不存在多个含义不明的 `final` 文件；未达到已批准样本量和门槛时，只给出候选排序，不声明最终推荐。
- **AC-003-07**：比较任务路径不再出现 `Path` 未定义；V2 验证不再引用未定义候选；验证字段和失败原因能通过 API 到达前端。
- **AC-003-08**：日志配置幂等，HTTP 与业务日志不重复注册 handler；算法日志包含 `task_id` 与 `algorithm_id`。
- **AC-003-09**：删除本地生成目录后，应用仍能创建必要运行目录并完成健康检查；大体积运行报告与模型/地图产物不会被误提交。
- **AC-003-10**：规格校验、漂移检查、快速测试、API 契约测试和指定集成测试全部通过；真实 benchmark 的未验证条件在清单中保持未完成。
- **AC-003-11**：三个 V2 算法成功时必须生成并返回查询图、最终位姿投影图和双图对比图；最终图必须对应返回的最终位姿，而不是迭代前的临时位姿。
- **AC-003-12**：同一匹配集、同一 NPY 的循环比较不得返回可用米制误差；单次定位只展示 2D 拟合诊断，并与需要独立 holdout 真值的 Benchmark 状态明确分离。
- **AC-003-13**：V2 定位任务基于最终位姿生成与查询图对齐的 XYZ NPY，并基于最终 2D–3D 内点拟合查询像素到 SLAM XY 的单应矩阵；查询图支持归一化选点，本地 API 按 `task_id/result_index` 返回、展示 `pixel_to_slam`、`npy_point` 与坐标差。运行时不得依赖 `slam-map` 服务，该结果也不得冒充独立位姿真值。
- **AC-003-14**：V2 与 SALAD+RoMa（原版）定位从最终 XYZ NPY 确定性采样有效像素，计算 H→SLAM XYZ 与 NPY XYZ 的多点三维差；`reliable` 只在中位坐标差严格小于 `0.3 m` 时为 true，等于或大于 `0.3 m` 均判为不准。内点数、相似度、2D 拟合和 LAS 邻近性仅作辅助诊断，不得单独产生“可信”状态。
- **AC-003-15**：SALAD+RoMa（原版）加载全局描述子缓存时必须校验缓存 key 与当前有效 tile key 的交集；不得把零交集的跨版本旧缓存当作可用索引。存在当前 V2 双描述子缓存时，原版复用其 `multi` 描述子并保留原版非对称检索语义；没有兼容缓存时才重建原版索引。进入局部匹配后必须调用 TinyRoMa，禁止以 LightGlue 实现冒充 RoMa 标签。
- **AC-003-16**：一致性判据必须比较 H→SLAM XYZ（Z=0）与 NPY XYZ 的三维欧氏距离，中位差严格 `<0.3 m` 才可判 `reliable=true`；不得仅比较 XY 平面距离而忽略 Z 分量，以免高度异常位姿被错误判为可靠。
- **AC-003-17**：精化步骤 (`refine_pose_with_roma`) 必须复用初始定位的匹配器（SALAD+RoMa 用 TinyRoMa），不得硬编码 LightGlue 导致算法不一致；应通过 `matcher_type` 参数分派，默认保持向后兼容。

## 成功标准

- 公开 API 的五算法分派契约达到 100% 自动化覆盖；
- 所有 P0 运行时未定义符号清零；
- 不再生成必然为 `0.0m` 的自比较精度；
- 相同代码、数据集和种子重复运行时，报告清单与算法配置一致；
- 算法推荐只有在真值数据和批准门槛齐备后才产生。
